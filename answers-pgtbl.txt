1.Which other xv6 system call(s) could be made faster using this shared page? Explain how.
answer:
在 xv6 中，除了 getpid() 之外，其他一些系统调用也可以通过共享页机制加速，尤其是那些频繁调用但无需真正进入内核态的数据查询型系统调用。例如，uptime() 是一个理想的候选，它返回自启动以来的时钟中断数，若内核将该值周期性地写入映射到用户只读共享页中的某个字段，用户程序即可通过 uuptime() 函数直接读取，避免一次系统调用的上下文切换。此外，如果 xv6 支持类似 UNIX 的 getppid()、getuid() 等系统调用，这些返回进程父 PID 或用户身份的调用通常也不频繁变化，同样可以作为共享页的一部分，静态分配字段，在进程创建时写入。这样一来，用户程序可以在完全用户态下获取这些基本信息，显著减少内核交互，提升性能。这种优化特别适用于高频调用或批量查询的场景，能有效降低系统调用开销。

2.Explain the output of vmprint in terms of Fig 3-4 from the text. What does page 0 contain? What is in page 2? When running in user mode, could the process read/write the memory mapped by page 1? What does the third to last page contain?
answer:
在 xv6 中，页表是三级结构，vmprint 函数的输出展示了每一级页表的有效项及其物理映射。最上层的页表被称为 page 0，它包含 512 个页表项，每项可能指向一个二级页表（也即 page 1）。当输出中出现形如 page table 0x... 的开头行后，随之而来的缩进形式 ..0:、..255: 等表明 page 0 中第 0 和第 255 项有效，其它项无效（未映射），这些有效项通常指向 page 1。

进一步进入 page 1（第二层页表），我们看到类似 .. ..0: 的缩进，这表示在第二层页表中，第 0 项有效，并继续指向 page 2（底层页表）。如果继续展开，有 .. .. ..0:、.. .. ..1: 等条目，则说明这些是 page 2 中的页表项，对应的是最终的用户空间虚拟地址所映射的物理页。也就是说，page 2 是三级页表结构中的叶子节点，其项直接映射数据页，如用户代码段、数据段或栈。

关于用户程序能否访问 page 1 中的内存，需要查看页表项中的权限位。通常，若该页表项设置了 PTE_R 和 PTE_U，则用户态程序可以读取该页；若还包含 PTE_W，则用户程序也可以写入。因此，是否可读写完全取决于映射时设置的权限。例如本实验中共享页 USYSCALL 被设置为 PTE_R | PTE_U，这意味着用户态只能读取该页中的内容而无法写入，从而保障内核数据的只读安全性。

最后提到的“第三到最后的页”是指底层页表中的第 509 项，它是页表中的倒数第三个有效映射页表项，对应的是一段高地址虚拟内存空间。在 xv6 中，这部分通常用作进程栈、堆顶或内核共享区域，具体内容可根据页表的初始化过程和系统映射策略判断。若其页表项具有用户读写权限（如 PTE_R | PTE_W | PTE_U），那么这部分很可能是用户数据段的一部分，可能用于动态内存分配或程序运行时栈空间。通过 vmprint 观察这些映射，不仅能直观理解虚拟地址空间的层级结构，也有助于调试内存分配、页面错误等问题。
